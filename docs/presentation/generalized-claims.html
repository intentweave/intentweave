Pre-release · 0.x

IntentWeave Claims

Repository statements that are backed by evidence, reviewed by people, and rechecked when the code changes.

Pre-release. The generalized repository Claims work lives on the branch feat/generalized-repository-claims and is not merged. IntentWeave is version 0.17.5. Compatibility surfaces (CLI output, JSON shapes, portable state, schema versions) may change in 0.x releases.

This presentation covers what the branch adds, how the pieces fit together, a worked example that runs end to end, and what is still missing. It makes no claim about AI precision: the AI-assisted curation step has no quality measurement yet.

1 · The problem

Documentation and configuration drift quietly

A repository says things about itself: a default timeout is 1800, the public function is documented, the endpoint requires authentication, the layers may not import each other. Those statements are written once and checked rarely. When the code moves, nothing says which statement is now wrong.

Claims make such a statement an explicit object. A Claim has a subject, a rule that checks it against the repository, evidence with provenance, and a human review. When the evidence changes, the Claim is reopened instead of silently passing.

2 · What is new

The lifecycle, end to end

Discovery→ Candidate→ Triage→ Promotion→ Claim→ Assessment→ Review→ Reopen

Candidates are not Claims

Discovery proposes statements. Nothing becomes governed until it is triaged and promoted explicitly, by a person or by a versioned Policy. Discovered findings are Candidates by default.

Assessments are reproducible

Checks are deterministic and make no model call. Each Assessment records its dependencies: the evidence versions and rule results it was built from.

Reopens are explained

claims check --since and claims explain show why a Claim was reopened, which evidence version changed, and which revisions were compared.

Subjects and continuity

A Claim has one or more Subjects. When a Subject moves or is renamed, continuity decides whether it is the same Subject. Unclear continuity is reported as inconclusive, never as a silent pass.

4 · Supporting layers

How the pieces fit together

Intent gate

iw intent check runs the existing Intent rules and the promoted Claims as one CI gate. A governed architecture violation is reported once.

Semantic correlation (opt-in)

iw claims discover --semantic may propose correlations for ambiguous findings. A model proposes; deterministic checks and review decide. Ambiguity that the code records is kept, even when a model says otherwise.

Observation layer

A complete inventory of files, modules, symbols, dependencies, and call sites per revision. Changes are derived from two complete runs. Coverage is per file, so one file that cannot be parsed does not blank the whole comparison.

Continuity gate

iw claims observations check --since reports unresolved continuity for Claim Subjects. It fails CI only when the reviewed config sets mode: gate. An upgrade never fails CI on its own.

Boundaries we keep

  • claims check never reads observation history. It uses persisted continuity and Git history at the reference revision.
  • Observation runs are pruned to the newest 20 runs plus the runs a command uses. Run headers stay, so provenance holds.
  • Subject bridges are created only on Candidate or Claim promotion.
5 · Worked example

A timeout default that changes

The 90-second demo (scripts/claims-90-second-demo.sh) runs this story on a temporary repository. The excerpts below are from a clean run at commit 25fdd58, with the build cache bypassed. The demo exited with code 0 in 5 seconds.

1. Discover and evaluate

{
  "gateStatus": "evaluated",
  "claims": [{ "parameterKey": "session.timeout", "claimType": "CLM-DEFAULT",
               "ruleStatuses": ["passed"], "assessmentStatuses": ["supported"] }],
  "candidates": { "discovered": 1, "active": 1, "issues": [] }
}
Initial claims exit: 4 (review required is expected)

Discovery found the default, but the Claim still needs a human review, so the check exits with 4.

2. Review and explain

session.timeout defaults to 1800
  Status: supported
  Type: Default value (CLM-DEFAULT)
  Check: passed
    Why: Literal binding found. (literal-binding-found)
  Review: accepted

3. Change the value and check against the merge base

Changed claims exit: 1 (contested plus an open reopen is expected)

session.timeout defaults to 3600
  Status: contested
  Reopen: Material change. (open, material-change)
    Dependency: evidence_version:evidence:91cadbf8…@2
    Provenance: {"changedPaths":["src/session.ts"], "materialChange":true, …}

The rule still passes, because the literal is present. The Claim is contested, because the evidence it was reviewed against has changed. A person must review it again.

A second example: continuity

In a seeded observation scenario, a file is renamed, and the new file contains two definitions with the same name. Git pairs the files, but the target is ambiguous:

symbol:function:src/a.ts#charge            continuity-unclear
symbol:function:src/c.ts#charge~1         continuity-unclear
symbol:function:src/c.ts#charge~2         continuity-unclear
file:src/a.ts                             moved
module:src/a.ts                           moved

The two overloads are not guessed to be the old function. The Subject is reported as unclear, and the gate treats it as unresolved for Claim Subjects.

7 · Status

What is done, and what is still missing

Done on this branch

  • Candidate, Claim, Assessment, Review, and reopen lifecycle
  • Five Claim families, with the endpoint and architecture slices
  • Observation layer, with per-file coverage, retention, and continuity links
  • Knowledge-graph tables and the Neo4j path removed; SQLite graph kept via plugin-kg-lite
  • 1313 tests in the full suite; the 90-second demo runs from a clean worktree

Still missing

  • Open: the AI-assisted curation quality gate: labelled sets from at least two more external repositories, plus a cost cap
  • Gated: policy-governed automation, which waits for that gate
  • Not done: external field reports from at least three repositories
  • Deferred: a different parser for the observation adapter; under 1.5% of files fail to parse in the three repositories measured, and the rewrites cover only two constructs
  • Not done: observation adapters for other languages
  • Partial: endpoint correlation beyond NestJS and one Fastify fixture
  • Not merged: the branch is open as PR #2

Decided against, on purpose

  • The implementation view stays in the local configuration and is not written into portable Claims state.
  • No time-based report period. The gate is enabled by a reviewed config change.
  • No automatic bridges for every observed object. Bridges need a promotion or a Review.
8 · The boundary

What IntentWeave does not claim

It gives a complete, reproducible inventory for each supported kind and scope, tracks the Subjects of Candidates and Claims, and reports changes between complete runs. It does not infer every relevant Claim from source code. Claims enter through Candidate discovery and explicit promotion, and that is a deliberate limit.

The labelled measurements so far are small. The observation detector agrees exactly with 55 seeded changes, but those labels were written alongside the detector, so they show consistency, not performance on unseen code. The Fastify reference of 14 registrations was measured on one external repository and is not re-measured here.
